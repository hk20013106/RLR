## 二、假说池数据模型（当前实现）

### 存储

SQLite append-only 数据库。所有变更以 event 追加，有 trigger 阻止 UPDATE/DELETE。

### 核心层级

```
families (假说族: 同一语句文本的集合)
  └── versions (假说版本: 不可变定义，含 operationalization + falsification_criteria)
        └── occurrences (候选×轮次 的具体实例)
```

### 两套状态投影

**Workflow（per occurrence）**：

```
PROPOSED → SELECTED → METHOD_DESIGNED → METHOD_APPROVED → EXECUTED → AUDITED → REVIEWED → RETAINED
   ↓           ↓            ↓
REJECTED   ARCHIVED    REJECTED → REVISION_REQUIRED → SUPERSEDED
```

**Epistemic（per hypothesis version，L9a 独家写入）**：

```
UNASSESSED → INSUFFICIENT_EVIDENCE / PROVISIONALLY_SUPPORTED / CONTRADICTED / FALSIFIED
```

### 方法存储

方法不是独立表，是 L4 delta 的一部分（strategies 数组，含 strategy_id, hypothesis_ids, steps）。L6 通过 analysis_plan 关联具体脚本。L7 执行结果记录在 evidence_records 表（source_kind=L7_RESULT）。

### 跨轮次

loop-memory JSON 传递：terminal_decision, required_new_search_directions, unexplored_branches, evidence_kept/dropped。下一轮 L10b 通过 next_round_proposal 创建新 hypothesis_id（DERIVED/REVISION_OF）。

### 关键约束

- 所有 reject/falsify/archive 都是事件记录，**永远不删除历史**
- Epistemic 状态是离散的 5 个值，不是连续概率
- Ranking 用 ELO 分数（advisory），不改变正式 gate 或 decision
- 没有贝叶斯后验分布计算

## 四、可视化方案

### 现状判断

**市面上没有开箱即用的系统能直接可视化 research loop 的假说池演化。** 现有工具要么只做存储（ideas/experiments），要么只做通用知识图谱。需要拼装。

### 推荐架构：三层

```
Obsidian (人类可读存储 + 编辑入口)
   ↓
SQLite ledger (已有，append-only event log)
   ↓
Streamlit + Plotly dashboard (交互式可视化)
```

**核心原则：LLM 负责产生/评估假说，可视化交给确定性脚本。** 不用 agent 做可视化。

### Obsidian 原生插件（零代码，快速但有限）

| 插件               | 能力                            | 局限            |
| ---------------- | ----------------------------- | ------------- |
| SQLite DB Viewer | 直接在 Obsidian 里写 SQL 查询 + 生成图表 | 手动查询，无自动化     |
| Dataview         | 基于 frontmatter 的表格/列表         | 不支持跨轮状态转移     |
| Excalibrain      | 图谱视图                          | 不适合版本 lineage |

**结论：Obsidian 插件适合快速查看，不适合科研级演化追踪。**

### Streamlit + Plotly 方案（推荐，10 行 Python 起步）

```bash
pip install streamlit pandas plotly
```

核心脚本只需读 SQLite → DataFrame → 图表。**不需要写 JSONL 中间层**，直接从已有 SQLite 读取。

### 5 个核心视图

| 视图               | 内容                                                                   | 实现                            |
| ---------------- | -------------------------------------------------------------------- | ----------------------------- |
| 1. 假说池总览         | 所有假说按 epistemic/workflow 状态分组                                        | stacked bar / treemap / table |
| 2. 跨轮次状态转移       | Round 1→2→3 的状态变化流                                                   | Sankey / alluvial diagram     |
| 3. 单假说演化 lineage | 版本树：v1→v2→v3 + 每步触发事件                                                | tree / timeline               |
| 4. 假说—实验—证据图     | Hypothesis/Experiment/Evidence 三类节点 + supports/contradicts/refines 边 | Cytoscape.js / pyvis          |
| 5. 单假说证据时间线      | 横轴 round，纵向列出每次事件（proposed/tested/supported/contradicted/final）      | Plotly timeline               |

### 最小可行版本（MVP）

只做 2 个文件：

1. `scripts/hypothesis_dashboard.py` — Streamlit app，从 SQLite 直接读取
2. 前 3 个视图（总览 + 转移 + lineage）

不引入新依赖（JSONL、parquet、Neo4j）。直接读已有 SQLite schema。

## 七、待讨论：文献检索归属（来自用户反馈）

### 当前设计

pre-research 没有明确归属 persona，是一个"前置 gate"，由 engine 在 L1/L4 运行前触发：

| 节点   | pre_research 类型                  | 实际执行者                  |
| ---- | -------------------------------- | ---------------------- |
| L1 前 | `deep_research`（学术文献检索）          | 跑 L1 的 agent（Einstein） |
| L4 前 | `literature_review`（方法论文献检索）     | 跑 L4 的 agent（Fisher）   |
| L7 前 | `code_search`（代码搜索）              | 跑 L7 的 agent（Turing）   |
| L8.5 | `literature_verification`（执行后验证） | Curie                  |

问题：Einstein 的核心能力是提出假说，Fisher 的核心能力是设计方法——文献检索不是他们的专业。让非专业角色做专业工作，质量不可控。

### 用户提出的方案

**Curie（L8）负责所有文献检索**，因为这是她的专业领域。具体：

| 当前                                | 改为                                              |
| --------------------------------- | ----------------------------------------------- |
| L1 前：Einstein 自己做 deep_research   | L1 前：Curie 先做 deep_research，Einstein 基于结果提出假说   |
| L4 前：Fisher 自己做 literature_review | L4 前：Curie 先做 literature_review，Fisher 基于结果设计方法 |
| L7 前：Turing 做 code_search         | 不变（代码搜索不是 Curie 的领域）                            |
| L8.5：Curie 做 post-execution 验证    | 不变                                              |

### 影响

- 需要在 topology 中新增 `L0.5`（Curie pre-L1）和 `L3.5`（Curie pre-L4）节点，或者在 L1/L4 的 `pre_research` 配置中指定 Curie 为执行者
- DAG 会变长：L0 → Curie(检索) → L1 → L2 → L3 → Curie(检索) → L4 → ...
- 优点：文献检索质量由专人负责，Einstein/Fisher 专注本职
- 缺点：DAG 变长，每轮耗时增加

### 替代方案（轻量级）

不新增节点，只改 `pre_research` 的 prompt 和 persona 标记：

- `pre_research` 阶段的 prompt 以 Curie 的口吻和要求编写
- 执行者仍然是 engine 在 L1/L4 前自动触发，但 prompt 中明确标注 "Curie persona"
- 不增加 DAG 深度

### 信息隔离设计

**Curie → Einstein 之间不需要信息隔离。** 文献检索结果是 L1 的前置输入，Einstein 应该完全看到。

当前机制：`_inject_pre_research` 把 pre-research 文件注入到 L1 context，有 4 种模式：

| 模式           | 行为                        |
| ------------ | ------------------------- |
| `digest`（默认） | 只注入 Runtime digest 摘要     |
| `excerpt`    | 注入截断全文（受 token budget 限制） |
| `full`       | 注入完整全文                    |
| `none`       | 不注入，只标记 "archived"        |

信息流（改后）：

```
Curie 做 deep_research → 写入 02_Agent_Notes/_pre_research/L1_research.md
                              ↓
Einstein 读取 L1_research.md → 基于结果提出假说
```

核心原则：Path B（认知隔离）隔离的是"DAG 允许的结构化输入"，不是"同一节点内的前置研究"。Curie 的文献检索属于 L1 的前置输入，Einstein 应该看到。同样，Curie 的 literature_review 结果 Fisher 也应该完全看到。

### 隔离 vs. 不隔离：实际折中方案

当前 `_inject_pre_research` 已内置 4 种模式，**默认 digest 就是软隔离**：

| 模式           | Einstein 看到什么 | Token 消耗    | 隔离程度 |
| ------------ | ------------- | ----------- | ---- |
| `none`       | 看不到           | 0           | 完全隔离 |
| `digest`（默认） | 只看摘要          | ~800 tokens | 软隔离  |
| `excerpt`    | 截断全文          | 可控          | 部分暴露 |
| `full`       | 完整全文          | 全量          | 无隔离  |

**结论：不需要在"隔离"和"不隔离"之间二选一。** 默认的 digest 模式已经是合理折中：

- Curie 写完整研究文件（存档，全量保存）
- Einstein 只看到 digest 摘要（~800 tokens，避免上下文污染）
- 关键是 digest 质量：太粗会遗漏信息，太细等于没隔离

改成 Curie 负责文献检索后，**不需要改隔离机制**，只需要确保 Curie 写的 digest 质量够高（关键发现 + 核心文献 + 研究空白）。

## 十一、待讨论：L3/L6 裁决标准缺失（来自用户反馈）

### 当前问题

L3（Oppenheimer 筛选假说）和 L6（Oppenheimer 批准方案）的 schema 只要求：

- L3：`disposition`（SELECTED/REJECTED）+ `reason_code`（自由文本）+ `reason`（自由文本）
- L6：`method_decision`（APPROVE/REJECT）+ `reason`（自由文本）

**没有预定义决策标准。** `reason_code` 不是枚举，agent 想写什么就写什么。没有排序逻辑，没有筛选依据。

### 用户提出的裁决标准

建议按以下四个维度评估，每个维度打分或二值判定：

| 维度                    | 说明                  | 适用节点  |
| --------------------- | ------------------- | ----- |
| **可检验性**（Testability） | 假说是否可以通过实验/分析验证或证伪？ | L3    |
| **新颖性**（Novelty）      | 假说是否提出新见解，而非重复已知结论？ | L3    |
| **可行性**（Feasibility）  | 当前资源/方法是否足以检验该假说？   | L3、L6 |
| **影响力**（Impact）       | 若假说成立，科学意义有多大？      | L3    |

### 建议实施

将 `reason_code` 改为枚举，将标准写入 L3/L6 的 `must` 规则：

```python
# L3 reason_code 枚举
"reason_code": {"enum": [
    "TESTABLE",           # 可检验
    "NOT_TESTABLE",       # 不可检验
    "NOVEL",              # 新颖
    "KNOWN_RESULT",       # 已知结论
    "FEASIBLE",           # 可行
    "INFEASIBLE",         # 不可行（资源/方法不足）
    "HIGH_IMPACT",        # 高影响力
    "LOW_IMPACT",         # 低影响力
]}
```

L3 筛选逻辑（伪代码）：

```
score(h) = w1*testable + w2*novel + w3*feasible + w4*impact
SELECT top-K by score (K ≤ 4)
REJECT the rest
```

L6 批准逻辑：

```
对每个 L4 strategy:
  if L5 attacks 中无 HIGH severity → APPROVE
  if L5 attacks 中有 HIGH severity 且无法解决 → REJECT
```
